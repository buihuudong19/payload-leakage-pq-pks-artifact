# Compared systems

All systems share the same interface (`src/pqpks/systems/`), the same HPKE key schedule (Export only), one-time AEAD
keys per image and the same payload framing; they differ only in the KEM and the encoding of its encapsulation
(`kem_part`), and in the embedder.

| System | Cryptographic layer | kem_part | Embedder |
|---|---|---|---|
| BL1 | EC-ElGamal P-256 + [RS16] mapping (reference implementation, RNG replaced by a CSPRNG) | decimal ASCII | sequential MPVD |
| BL2 | HPKE ML-KEM-768 | raw, 1088 B | sequential MPVD |
| BL3 | HPKE DHKEM(P-256) | uncompressed point, 65 B | two-stage HILL-STC |
| BL4 | HPKE DHKEM(P-256) + point encoding of [Zha25] (adaptation, see below) | 72 B, near uniform | two-stage HILL-STC |
| BL4-E | HPKE DHKEM(X25519) + Elligator 2 (cross-check for BL4) | 32 B, near uniform | two-stage HILL-STC |
| BL5 | HPKE ML-KEM-768 | raw, 1088 B | two-stage HILL-STC |
| BL5-L | HPKE ML-KEM-768, length-matched control (uniform padding) | 1088 + 448 B | two-stage HILL-STC |
| PQ-PKS | HPKE ML-KEM-768 + Kemeleon, main variant (default) | 1536 B, near uniform | two-stage HILL-STC |
| PQ-PKS-R | HPKE ML-KEM-768 + Kemeleon, rejection-sampled variant (ablation A4) | 1252 B, near uniform | two-stage HILL-STC |
| REF-U | reference: uniform payload with the length and layout of PQ-PKS | 1536 B, uniform | two-stage HILL-STC |
| REF-1S | reference: uniform payload of the same total length | - | single-stage HILL-STC |

## BL1: reference implementation

BL1 runs an earlier EC-ElGamal + MPVD implementation unchanged, except that its random number generator is replaced
by `secrets.SystemRandom()` (`src/pqpks/systems/mpvd_systems.py`). That code is not redistributed. To run BL1, or the
test that checks the single-channel MPVD port bit for bit against it (`tests/test_mpvd_equivalence.py`), place the
reference modules (`ECCurve.py`, `ECencrypt.py`, `ECdecrypt.py`, `Embed.py`, `Extract.py`, `TextToBin.py`,
`BinToText.py`, `mod_sqrt.py`, `PicToData.py`) in `baselines/bl1_reference/` or set `PQPKS_BL1_REFERENCE_DIR`.
Without them these tests are skipped and the BL1 rows of the pilot and cross-check scripts cannot be produced; the
confirmatory scripts (`scripts/confirm/`, `scripts/experiments/`) do not use BL1.
The SHA-256 of the nine modules used in the pilot rounds are published in `baselines/bl1_reference.SHA256SUMS`;
`python scripts/setup/check_bl1_reference.py [folder]` checks a local copy against them. BL1 was run only in the pilot
rounds (`results/archive/pre-confirm/pilot_baselines/` of the dataset record) and enters no result of the article.

## BL4: adaptation of [Zha25] to the image channel

**Source.** Repository https://github.com/XinZhang1999/Public-key-Discop, commit
`a03633c6fbd343852798a872a9b52e98f8984f8f`, file `src/PRNEncryption_P256.py`. The repository has no license file, so
the module is not redistributed; `scripts/setup/fetch_third_party.py` downloads that exact file and checks its SHA-256
(`third_party/zha25_public_key_discop/SHA256SUMS`). `src/pqpks/crypto/zha25.py` loads it without modification.

**Kept from [Zha25].**

- Point hiding: `encode(P, rnd)` represents a point P as forward_map(u) + forward_map(v), where forward_map is the SWU
  map on P-256 (an admissible encoding in the style of Elligator Squared).
- Bias elimination: `encode_bytes(x, p, LT, 256)` = x + k p with random k such that the result is < 2^(256+LT).
  LT = 32 as in the original code, so each part has 36 B and kem_part has 72 B.

**Changed, and why.**

1. Channel. The original work embeds with Discop in text generated by a language model. Here the payload is embedded
   with the two-stage HILL-STC embedder, as for BL3, BL5 and PQ-PKS, so BL4 is an adaptation, not a reproduction of the
   original system.
2. Shared key. It comes from HPKE DHKEM(P-256), as in BL3: `enc` is the ephemeral point and the shared key is
   ECDH(eph, pk_R). The encoder of [Zha25] only changes the serialization of `enc` (65 B uncompressed point to 72 B near
   uniform). BL3 and BL4 therefore differ in exactly one factor, and BL4 against PQ-PKS compares DDH with MLWE inside
   the same HPKE framework.
3. Only `encode`, `decode`, `PRNEncryption_P256.encode_bytes` and `decode_bytes` are used. The methods `encrypt` and
   `decrypt` of the published module are not used.

**Quantitative notes.**

- The statistical distance of the bias elimination is about 2^-LT = 2^-32 per element, larger than the 2^-76 of
  Kemeleon (t = 76); this parameter must be kept in mind when BL4 is compared with PQ-PKS.
- Every pair (u', v') decodes to a valid point (50 random 72-byte strings all gave an HPKE context), so, as with the
  implicit rejection of ML-KEM, the receiver does not reveal a point-decoding failure (`tests/test_baselines.py`).
